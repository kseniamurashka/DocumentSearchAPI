1. Роли компонентов проекта

Пользователь вводит слова, а сервис возвращает подходящие тексты с рубриками и датой. Для этого мы разделили хранение полных записей и полнотекстовый поиск.

Одна логическая запись CSV — один документ нашего приложения. Поле с текстом может содержать переносы строк, поэтому физическая строка файла и запись CSV не всегда совпадают. «Документ» здесь не означает отдельный Word-файл.

В нашем CSV нет ID. Его создаёт PostgreSQL при вставке. Затем мы используем этот ID в обоих хранилищах. Наличие пропусков в последовательности ID допустимо: ID — идентификатор, а не номер строки для пользователя.

PostgreSQL выбран основным источником полных данных. Поисковое представление можно построить из него повторно. Это архитектурное решение нашего проекта; Elasticsearch не требует PostgreSQL для своей работы.

2. Документ, индекс и _id

Elasticsearch работает с JSON-документами. Индекс объединяет документы и правила обработки их полей. Например, индекс documents содержит поисковые представления наших записей.

{
    "id": 42,
    "text": "В городе открылась новая библиотека"
}

Слово «индекс» перегружено. Индекс Elasticsearch — именованная коллекция документов и связанных поисковых структур. Индекс PostgreSQL на created_date — вспомогательная структура для ускорения некоторых SQL-запросов. Это разные понятия.

Основа: Elasticsearch: indices, documents and fields.

Служебный _id и обычный id

{
    "_index": "documents",
    "_id": "42",
    "_source": {
        "id": 42,
        "text": "В городе открылась новая библиотека"
    }
}

_id идентифицирует документ внутри индекса. _source содержит его исходные поля. id внутри _source — поле, которое мы сами добавили по условию задания. Равенство этих идентификаторов обеспечивается нашим кодом.

При индексации задаём "_id": str(document.id). При чтении из поискового ответа делаем обратное преобразование: int(hit["_id"]). Аннотация list[int] сама по себе строки в числа не превращает.

Шарды и реплики

Шард — часть индекса. Первичные шарды распределяют данные; реплики хранят копии первичных шардов. Для нашего небольшого локального набора выбраны один первичный шард и ноль реплик. Реплику нельзя разместить на том же узле, что и её первичный шард.

Ноль реплик не означает «ничего не сохраняется»: данные первичного шарда сохраняются в хранилище Elasticsearch. Docker volume позволяет сохранять их при пересоздании контейнера. Реплика и резервная копия решают разные задачи: обычное удаление документа распространяется и на реплики.

3. Как текст превращается в поиск

Упрощённая идея полнотекстового индекса: для каждого термина хранить, в каких документах он встречается. Такая структура называется инвертированным индексом.

Исходные документыУсловная поисковая структура
1: «кот спит»
2: «кот играет»
3: «пёс спит»		кот → 1, 2
спит → 1, 3
играет → 2
пёс → 3

По слову «кот» можно сразу найти кандидатов 1 и 2. Таблица выше намеренно упрощена: реальные поисковые структуры содержат дополнительную информацию, например позиции и частоты терминов.

Анализатор

Анализатор преобразует текст в токены — единицы для индексирования и поиска. Типичный процесс: разделение текста, приведение регистра и фильтрация. Языковой анализатор russian включает обработку русских стоп-слов и стемминг. Стемминг сокращает слова по правилам; это не полноценное понимание грамматики или смысла.

Разные формы слова могут дать одинаковый термин, но не нужно обещать совпадение всех словоформ и однокоренных слов. Оригинальный текст в _source сохраняется, даже если его поисковое представление изменилось.

Устройство языкового анализатора: Russian analyzer.

Запрос match тоже проходит анализ. Поэтому сравниваются обработанные термины запроса и документа. У нас нет настроенных синонимов, векторного поиска или автоматического понимания темы текста.

Подумай. Почему нельзя проверять наш поиск только выражением query in document.text в Python?
Ответ

Проверка подстроки сравнивает символы, а поиск использует обработанные термины. Регистр, окончания и стоп-слова могут влиять на эти способы по-разному.

4. Mapping и ensure_index

Mapping описывает типы полей и способы их индексирования. Для текста, числа и даты нужны разные правила.

mappings={
    "dynamic": "strict",
    "properties": {
        "id": {"type": "long"},
        "text": {"type": "text", "analyzer": "russian"},
    },
}
  • long — 64-битное целое число.
  • text — поле для полнотекстового поиска с анализом.
  • keyword обычно используют для значений, которые нужно сопоставлять целиком: код, статус, метка. Это полезный альтернативный тип, но в нашем mapping его нет.
  • dynamic="strict" запрещает неизвестные поля. Это не требование обязательного присутствия всех объявленных полей.

Изменение mapping существующего поля ограничено. Например, смена принципа анализа уже проиндексированного текста обычно требует создания нового индекса и повторного индексирования.

Подробнее: Mapping.

async def ensure_index(client):
    if await client.indices.exists(index=settings.elasticsearch_index):
        return

    await client.indices.create(
        index=settings.elasticsearch_index,
        settings={"number_of_shards": 1, "number_of_replicas": 0},
        mappings={
            "dynamic": "strict",
            "properties": {
                "id": {"type": "long"},
                "text": {"type": "text", "analyzer": "russian"},
            },
        },
    )

Первый запрос проверяет существование индекса. Если индекс есть, функция ничего не меняет. Если нет — создаёт пустой индекс. Загрузка документов выполняется другой функцией. Аргумент settings= в вызове создания — настройки Elasticsearch; объект settings.elasticsearch_index справа — настройки нашего приложения.

Правка Python-словаря в ensure_index не обновляет уже существующий индекс: ранний return не даёт выполнить создание. Также «проверить, затем создать» — две операции: при одновременном запуске нескольких инициализаторов возможна гонка.

5. Запросы и релевантность

{"query": {"match": {"text": "новая библиотека"}}}

В нашем match действует логика OR по терминам после анализа: достаточно совпадения хотя бы одного. Это не требование точного вхождения всей фразы.

{"query": {"match": {
    "text": {"query": "новая библиотека", "operator": "and"}
}}}

Вариант с AND требует совпадения всех полученных терминов. Он показан для сравнения; менять поведение проекта без отдельного решения не нужно. Если анализ удалил все термины, стандартное поведение match — не вернуть совпадений.

Параметры и логика: Match query.

ИнструментДля чего используют
matchПоиск анализируемого текста.
match_phraseПоиск последовательности анализируемых терминов с учётом позиций. Это не буквальное сравнение исходных строк.
termПоиск точного индексированного термина без обычного анализа текста запроса; часто подходит для keyword.
boolОбъединение условий: обязательных, исключающих, фильтрующих и других.

Elasticsearch может рассчитывать _score, оценку релевантности. Большая оценка не означает более свежий документ. В нашем задании окончательный порядок задаётся датой, поэтому ранжирование Elasticsearch не определяет порядок ответа API.

Пример. Найдено 100 документов. Документ №100 по релевантности — самый новый. Если взять в Elasticsearch только первые 20 по релевантности, последующая сортировка этих 20 по дате не вернёт документ №100. Поэтому сначала определяем все совпадения.

6. Индексирование, bulk и refresh

Индексирование — запись документа в Elasticsearch с построением поисковых структур. Наша функция читает из PostgreSQL только нужные для этого поля:

result = await session.execute(select(Document.id, Document.text))
documents = result.all()

actions = [
    {
        "_op_type": "index",
        "_index": settings.elasticsearch_index,
        "_id": str(document.id),
        "_source": {"id": document.id, "text": document.text},
    }
    for document in documents
]

indexed_count, _ = await async_bulk(
    client, actions, chunk_size=500, refresh="wait_for",
)

Список actions описывает будущие операции. Его создание ещё не обращается к Elasticsearch. Вызов async_bulk отправляет операции пакетами. chunk_size=500 — максимум операций в пакете; ограничение размера пакета в байтах тоже может привести к его разделению.

Операция index с тем же _id заменяет существующий документ. Поэтому повторная индексация одинаковых записей не добавляет новые копии. Но этот скрипт не удалит старую запись из индекса, если её уже нет в PostgreSQL.

indexed_count — число успешных операций, а не число исключительно новых документов. Переменная _ обозначает неиспользуемую часть результата. По умолчанию ошибки операций могут вызвать исключение; ранее успешные операции при этом не откатываются как единая транзакция.

Асинхронный клиент и helpers: Using with asyncio.

Когда запись видна поиску

Успешная запись и видимость записи для поиска — разные события. Операция refresh делает изменения доступными поиску. refresh="wait_for" ждёт соответствующего обновления. Это не SQL-коммит и не общая транзакция с PostgreSQL.

Механизм видимости: Near real-time search; параметр ожидания: Delete API, refresh.

7. Получение всех совпадений

async def search_document_ids(client, query: str) -> list[int]:
    document_ids = []

    async for hit in async_scan(
        client,
        index=settings.elasticsearch_index,
        query={
            "query": {"match": {"text": query}},
            "_source": False,
        },
        size=500,
    ):
        document_ids.append(int(hit["_id"]))

    return document_ids

async_scan получает совпадения порциями, а async for перебирает отдельные результаты. hit — один результат поиска. size=500 задаёт размер порции на шард, а не общее ограничение поиска.

_source=False исключает исходные поля из ответа, но оставляет служебный _id. Порядок обхода scan не следует считать ни порядком релевантности, ни порядком даты.

Для нашего набора из 1500 записей собрать ID в память удобно. При миллионах совпадений возрастут расход памяти, размер SQL-условия и время ответа. Тогда нужно пересматривать архитектуру: например, согласовать хранение даты в поисковом индексе и получать отсортированную страницу там. Это возможное развитие, а не текущая реализация.

Обычный поиск Elasticsearch и helper async_scan — разные интерфейсы. В нашем helper аргумент query содержит полное тело поиска, поэтому внутри него есть ещё ключ "query". В прямом вызове client.search(query=...) форма аргумента другая.

8. SQLAlchemy, ORM и модели

SQLAlchemy предоставляет инструменты работы с SQL. Условно выделяют Core — выражения SQL, таблицы и соединения — и ORM, которая связывает Python-классы с таблицами и отслеживает изменения объектов. ORM не отменяет SQL: понимать SELECT, INSERT, UPDATE, DELETE и транзакции по-прежнему нужно.

class Base(DeclarativeBase):
    pass

class Document(Base):
    __tablename__ = "documents"

    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    rubrics: Mapped[list[str]] = mapped_column(ARRAY(Text), nullable=False)
    text: Mapped[str] = mapped_column(Text, nullable=False)
    created_date: Mapped[datetime] = mapped_column(
        DateTime(timezone=False), nullable=False, index=True,
    )
Часть объявленияСмысл
DeclarativeBaseОснова декларативных ORM-моделей; наш Base сам таблицей не является.
__tablename__Имя таблицы PostgreSQL.
Mapped[int]Аннотация ORM-атрибута Python.
mapped_columnНастройки соответствующего столбца.
primary_key=TrueПервичный ключ: идентификация строки.
nullable=FalseЗапрет SQL NULL; пустую строку сам по себе не запрещает.
ARRAY(Text)Массив текстовых значений PostgreSQL.
index=TrueОбъявление SQL-индекса. Не задаёт порядок выдачи без ORDER BY.

Объявление таблиц: SQLAlchemy: Table Configuration.

Создание Document(text=..., ...) создаёт Python-объект. До добавления в сессию и выполнения SQL записи в PostgreSQL ещё нет. В нашем исходном наборе даты без часового пояса, поэтому выбран DateTime(timezone=False). Это свойство данных проекта, а не универсальное правило для всех сервисов.

Engine хранит конфигурацию доступа и управляет пулом соединений. Пул позволяет повторно использовать соединения вместо постоянного открытия новых. Само создание engine обычно ещё не устанавливает соединение с сервером.

pool_pre_ping=True проверяет соединение при выдаче из пула и помогает заменить устаревшее. Он не гарантирует доступность базы и не повторяет автоматически прерванную бизнес-транзакцию. await engine.dispose() освобождает ресурсы пула при завершении работы.

Пул и проверки соединений: Connection Pooling.

session_factory создаёт отдельные сессии. Session отслеживает ORM-объекты и участвует в управлении транзакцией. Она не равна одному SQL-запросу и не является глобальным кешем всей базы.

expire_on_commit=False оставляет уже загруженные атрибуты доступными после коммита без автоматического истечения их состояния. Это не делает их автоматически актуальными при изменениях из других запросов.

Назначение сессии: Session Basics.

Один engine можно использовать во всём приложении. Одну изменяемую AsyncSession нельзя совместно использовать в нескольких одновременно выполняющихся задачах: каждой нужна своя сессия. См. AsyncSession и concurrent tasks.

10. Чтение: select, scalar, scalars

select(...) строит описание запроса. Обращение к базе происходит при его выполнении через сессию.

statement = (
    select(Document)
    .where(Document.id.in_([42, 108, 315]))
    .order_by(Document.created_date.desc(), Document.id.asc())
    .limit(20)
)
result = await session.scalars(statement)
documents = result.all()

Условный SQL:

SELECT id, rubrics, text, created_date
FROM documents
WHERE id IN (42, 108, 315)
ORDER BY created_date DESC, id ASC
LIMIT 20;

Это поясняющий SQL. В реальном выполнении SQLAlchemy передаёт значения как параметры. Не нужно собирать SQL через f-строку с пользовательским вводом.

ВызовЧто удобно получитьПример
await session.execute(...)Строки с несколькими выбранными значениямиselect(Document.id, Document.text)
await session.scalars(...)Первые элементы каждой строки: например, ORM-объектыselect(Document)
await session.scalar(...)Первое значение первой строки или Noneselect(Document.id).limit(1)

После обычного await session.scalars(...) вызов result.all() синхронный: для этого буферизованного результата не нужен ещё один await. Потоковые API имеют другой интерфейс.

Формы результатов: Writing SELECT statements.

scalar() не означает «проверить, что строка ровно одна». Если нужна такая проверка, используются методы вроде scalar_one() и scalar_one_or_none() у результата.

Порядок значений в IN (...) не задаёт порядок ответа. Его определяет только ORDER BY. Дополнительная сортировка по ID делает результат однозначным при совпадающих датах.

11. Запись и транзакции

Транзакция объединяет изменения PostgreSQL: успешный commit фиксирует их, rollback отменяет незафиксированную работу этой транзакции. Например, импорт может добавить сразу много документов, но не оставить половину вставок при обычной ошибке внутри транзакции.

async with session_factory.begin() as session:
    session.add_all(documents)
# Успешный выход: commit, затем закрытие сессии.
# Исключение внутри блока: rollback и закрытие.

async with session_factory() as session только управляет временем жизни сессии и не обещает commit при выходе. session_factory.begin() дополнительно задаёт границы транзакции с commit/rollback.

Контекст транзакции: Transactions and Connection Management.

ОперацияЧто происходит
session.add(obj), add_all(...)Объекты ставятся на учёт в сессии. Вставка может произойти позже.
await session.flush()Накопленные изменения отправляются в PostgreSQL, но транзакция ещё не фиксируется.
await session.commit()Выполняется необходимый flush, затем фиксируется транзакция.
await session.rollback()Откатывается текущая транзакция.
await session.delete(obj)ORM-объект помечается для удаления; SQL DELETE выполняется при flush.

Операции сессии: Session Basics.

Пример: получить выданный PostgreSQL ID

async with session_factory.begin() as session:
    document = Document(
        text="Учебный документ",
        rubrics=["учёба"],
        created_date=datetime(2026, 9, 27, 12, 0),
    )
    session.add(document)
    await session.flush()
    print(document.id)  # INSERT уже выполнен, ID получен.
# Здесь транзакция успешно фиксируется.

Если после flush случится исключение до коммита, вставка может быть отменена. При этом значение последовательности ID PostgreSQL может остаться потраченным. Поэтому после rollback возможен пропуск в номерах.

Почему наш повторный импорт возвращает 0

existing_id = await session.scalar(select(Document.id).limit(1))
if existing_id is not None:
    return 0
session.add_all(documents)

Этот код проверяет наличие хотя бы одной записи. Он не сравнивает содержимое CSV со строками таблицы. Это простая защита повторного первоначального импорта, а не универсальное устранение дубликатов. Дополненный CSV не загрузится в непустую таблицу; удалённую одну запись таким импортом тоже не восстановить.

13. Асинхронность и lifespan

async def объявляет корутинную функцию. Её вызов создаёт объект корутины; для выполнения нужен await или запуск через цикл событий. await на асинхронном вводе-выводе даёт другим задачам возможность выполняться, пока текущая ждёт сервер.

Это полезно при сетевых запросах к PostgreSQL и Elasticsearch. Асинхронность не превращает тяжёлый вычислительный цикл Python в параллельный и не делает любой код внутри async def неблокирующим.

@asynccontextmanager
async def lifespan(app: FastAPI):
    try:
        async with AsyncElasticsearch(
            settings.elasticsearch_url,
            request_timeout=30,
        ) as client:
            app.state.elasticsearch = client
            yield
    finally:
        await engine.dispose()

До yield выполняется подготовка приложения. На yield управление передаётся FastAPI: приложение принимает запросы. При штатном завершении управление возвращается, клиент закрывается контекстным менеджером, затем освобождается пул PostgreSQL. finally нужен для очистки и при исключениях; он не является гарантией выполнения при принудительном уничтожении процесса.

app.state.elasticsearch — сохранённый объект клиента. Его создание не доказывает доступность сервера: реальная проблема связи может проявиться при первом запросе.

Время жизни общих ресурсов: FastAPI lifespan.

14. Весь путь поискового запроса

q: текст
Проверка ввода
→
Elasticsearch
Все подходящие ID
→
PostgreSQL
Сортировка и LIMIT 20
→
Pydantic
JSON с 4 полями

Вспомним ответственность каждого этапа:

  1. FastAPI проверяет, что q передан и содержит хотя бы один непробельный символ.
  2. q.strip() убирает пробелы с краёв. Оно не исправляет орфографию и не меняет логику поиска.
  3. Elasticsearch анализирует запрос и определяет совпадения.
  4. Если ID нет, API возвращает пустой список без чтения документов PostgreSQL.
  5. SQL выбирает полные документы с найденными ID, сортирует по дате убывающе и по ID возрастающе, ограничивает результат двадцатью.
  6. Схема ответа преобразует атрибуты в JSON. Даты представлены строками соответствующего формата.

Допустим, совпали ID [7, 2, 9], а даты у них соответственно 10, 12 и 11 сентября. Итоговый порядок будет [2, 9, 7], независимо от порядка ID, который вернул Elasticsearch.

Если в индексе есть устаревший ID, которого уже нет в PostgreSQL, SQL не создаст для него запись. Но это не исправит сам индекс: контроль согласованности — отдельная задача.

Принятая нами трактовка задания: до 20 самых новых документов среди всех совпадений. Формулировка «первые 20, упорядоченные по дате» может требовать уточнения у заказчика; в README следует явно зафиксировать выбранное поведение.

15. Удаление и согласованность

Это схема предложенного следующего шага разработки. По ID находим строку PostgreSQL, удаляем документ из Elasticsearch, затем фиксируем удаление в PostgreSQL.

async with session_factory.begin() as session:
    document = await session.scalar(
        select(Document)
        .where(Document.id == document_id)
        .with_for_update()
    )
    if document is None:
        raise HTTPException(status_code=404, detail="Document not found")

    await delete_document_from_index(client, document_id)
    await session.delete(document)

with_for_update() блокирует найденную строку PostgreSQL на время транзакции. Другой запрос на изменение или блокирующее чтение той же строки обычно должен ждать. Обычный SELECT благодаря MVCC не обязан ждать эту блокировку. Блокировка PostgreSQL не блокирует Elasticsearch.

Для Elasticsearch удаление выполняется по имени индекса и _id. Отсутствие самого документа можно принять как уже достигнутое состояние. Отсутствие целого индекса — отдельная ситуация; не нужно безусловно скрывать любой ответ 404.

Операция удаления: Elasticsearch Delete API.

Почему две операции не становятся одной транзакцией

СитуацияРезультат и действие
Elasticsearch недоступен до удаленияТранзакция PostgreSQL откатывается; основная запись остаётся.
Elasticsearch удалил запись, затем PostgreSQL откатилсяЗапись остаётся в базе, но исчезает из поиска. Повторное удаление может завершить операцию, если «уже нет в индексе» обработано.
Оба удаления завершилисьОтвет 204 без тела.
PostgreSQL уже не содержит IDНаш endpoint возвращает 404. Он не выполняет универсальную очистку всех возможных остатков в индексе.

Таймаут тоже неоднозначен: сервер мог выполнить действие, но ответ не успел дойти. Поэтому операции, которые можно безопасно повторять, полезны. Идемпотентность описывает одинаковое итоговое состояние при повторении, а не обязательное равенство HTTP-ответов.

Для более строгой синхронизации применяют хранение заданий на доставку изменений в той же транзакции PostgreSQL (outbox) и повторную обработку. Это дополнительная архитектура, не обязательная для нашего небольшого учебного решения. Одновременный полный запуск индексатора и удалений тоже требует согласования: индексатор мог заранее прочитать удаляемую запись и записать её в индекс позже.

16. Ошибки и диагностика

Наша ошибка в except

# Неверно: второй элемент — класс клиента.
except (ApiError, AsyncElasticsearch) as exc:
    ...

# Верно: оба элемента — классы исключений.
from elastic_transport import TransportError

except (ApiError, TransportError) as exc:
    raise HTTPException(
        status_code=503,
        detail="Search service unavailable",
    ) from exc

На успешном запросе блок перехвата не требуется. Когда соединение с Elasticsearch обрывается, Python проверяет обработчик и обнаруживает класс, не наследующийся от BaseException. Возникает TypeError, и вместо предусмотренного 503 можно получить 500. В нашей проверке это воспроизводилось искусственной ошибкой соединения, без остановки контейнера.

raise ... from exc связывает новую ошибку с исходной для диагностики. Клиенту API можно отдать короткое описание, а в логах сохранить техническую причину. Пароли и полный URL с учётными данными в сообщения пользователю не включают.

СимптомЧто проверить

422Входные параметры: есть ли q, не состоит ли он из пробелов, корректен ли ID.

Успешный /health в текущем проекте проверяет PostgreSQL через SELECT 1. Он не доказывает доступность Elasticsearch, наличие таблицы documents или правильность индекса. Название проверки не заменяет чтение её кода.

17. Задания с ответами

Сначала сформулируй ответ самостоятельно, затем раскрой пояснение. Для этих заданий не нужны серверы или интернет.

1. Создали Document(...). Появилась ли запись в PostgreSQL?

Нет. Пока создан Python-объект. Его нужно добавить в сессию, выполнить flush и успешно зафиксировать транзакцию для сохранения результата.

2. Чем flush отличается от commit?

Flush отправляет изменения в БД внутри текущей транзакции. Commit завершает её фиксацией. После flush ещё возможен rollback.

3. Почему после удаления ID 42 следующая запись не обязана получить 42?

Генератор ID не предназначен для заполнения пропусков. Уникальность важнее непрерывности. Откаты и удаления могут оставлять пропуски.

4. Что вернёт scalars(select(Document.id, Document.text))?

Первые элементы строк результата, то есть ID. Чтобы получать обе колонки, используй execute и строки результата.

5. size=500 в async_scan: будет ли потерян 501-й документ?

Нет. Helper получает следующие порции. Размер порции не равен общему пределу совпадений.

6. Зачем _source=False, если нам нужен ID?

Мы используем служебный _id, который остаётся в ответе. Передавать весь текст и обычное поле id для этого не нужно.

7. Два запуска индексатора дали по 1500 успешных операций. В индексе теперь 3000 документов?

Не обязательно. При тех же _id операция index заменяет существующее содержимое. Число успешных операций не равно приросту числа документов.

8. dynamic=strict требует, чтобы text всегда присутствовал?

Нет. Он запрещает неизвестные поля. Обязательность полей — другая проверка.

9. Изменили analyzer в ensure_index, перезапустили скрипт. Применился ли он?

Если индекс уже был, наша функция сразу вернулась. Нужно отдельно продумать изменение индекса и повторную индексацию.

10. Почему сортировка только по дате может давать неоднозначный порядок?

Несколько документов могут иметь одинаковую дату. Второй ключ сортировки id задаёт устойчивый порядок между ними.

11. Можно ли передать одну AsyncSession двум задачам через asyncio.gather?

Для независимой параллельной работы так делать не следует: сессия хранит изменяемое состояние транзакции. Каждой задаче нужна собственная сессия.

12. Откат PostgreSQL вернёт документ в Elasticsearch?

Нет. Транзакция PostgreSQL не управляет уже выполненной операцией другого сервиса.

13. Почему в except нельзя написать AsyncElasticsearch?

Это класс клиента, а не исключения. При обработке сбоя Python может выбросить TypeError из-за недопустимого класса в except.

14. После удаления одной записи запустили наш импорт CSV. Она восстановится?

Нет, если в таблице остались другие записи: проверка непустой таблицы завершает импорт с результатом 0.

15. В коде endpoint есть ORDER BY и LIMIT 20. Достаточно ли этого для проверки поиска?

Нет. Нужно проверить, что ID действительно соответствуют запросу, ограничение применяется после отбора всех совпадений, возвращаются все нужные поля, а ошибки и пустые запросы обработаны.

Практическая задача на бумаге

Elasticsearch вернул ID [5, 9, 2, 8]. В PostgreSQL есть: 5 — 10 сентября, 9 — 12 сентября, 2 — 12 сентября. ID 8 отсутствует. Каков результат сортировки created_date DESC, id ASC?

Проверить решение

[2, 9, 5]. Сначала две записи за 12 сентября, между ними меньший ID раньше. Отсутствующий ID 8 не порождает документ в SQL-ответе.

Небольшая задача на код

Напиши запрос SQLAlchemy, выбирающий максимум пять документов, созданных не раньше 1 сентября 2026 года, начиная с новых. Сравни с решением.

Возможное решение
statement = (
    select(Document)
    .where(Document.created_date >= datetime(2026, 9, 1))
    .order_by(Document.created_date.desc(), Document.id.asc())
    .limit(5)
)
async with session_factory() as session:
    result = await session.scalars(statement)
    documents = result.all()

Это учебная дата. В нашем исходном CSV записи за 2019 год, поэтому на исходном наборе такой запрос вернёт пустой список.
